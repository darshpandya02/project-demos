Robot factory: primary-backup replication

C++11TCP socketsthreads

Programming assignment 3 of Building Scalable Distributed Systems. Customers order robots and read their customer records from a "factory" server. Each connection gets an engineer thread. Orders go through a single admin thread, which appends each one to a log, replicates it to every backup factory, and only then updates the customer record and ships the robot.

The code has no fixed primary. The first factory that receives an order becomes the primary and connects to its peers. The peers then act as backups: they write each entry into their own log and apply it once a later message carries a higher commit index. If the primary loses a backup, it skips that backup and tries to reconnect on every later order. When the reconnect succeeds, it replays its committed log to the backup before sending new entries. If the primary dies, clients can send orders to a backup, which then takes over as primary with the data it already has.

What the recording shows

  • A fresh git clone of the repository, built with make CXX=clang++. There is one compiler warning, for an unused counter.
  • Three factories on ports 12000 to 12002. Each one is given the other two as peers.
  • 8 customer threads each place 2,000 orders on 12000, which becomes the primary: about 8,200 orders/s, with an average latency of about 1 ms. Then 8 × 2,000 record reads: about 75,000 reads/s. Reads are served locally and need no replication.
  • A record dump from backup 12001 shows the replicated customer table. One entry is one order behind (see below).
  • Backup 12002 is killed with SIGKILL. The primary skips it and 2,000 more orders go through.
  • 12002 is restarted with empty state. The next order makes the primary reconnect and replay its whole committed log, about 18,000 entries. That order took about 1.8 s, which is the large max latency on that line. Afterwards 12002's dump matches the primary.
  • The primary 12000 is killed. Orders sent to 12001 succeed: 12001 takes over as primary, fails to reach 12000, and replicates to 12002. Dumps from 12001 and 12002 show the new orders.

Other heavy jobs were running on the laptop during this recording (load average around 30 to 60). In an earlier trial run of the same script on the same machine, with less load, the first order run reached about 32,000 orders/s at about 0.25 ms average latency.

Behaviour worth knowing

  • A backup applies an entry only when the next replication message raises the commit index, so its copy of the most recent order lags by one. That is why the dump from a backup can show 1998 for one customer while the primary has 1999.
  • When a backup takes over, the last entry it received from the old primary was never marked committed, so that one order is not applied to the new primary's records.
  • Replication to the backups is sequential and happens inside the single admin thread. Every order waits for all live backups, so order throughput is bounded by one round trip per backup per order.
  • The client reports latencies in microseconds and throughput in requests per second, measured over the whole run.
